STARK STUDIO — IMPLEMENTATION AND ACCEPTANCE PLAN
=================================================
Revised: 21 September 2026
Target: Fedora 44 desktop, PySide6 / Qt Widgets
Historical source-of-truth statement retired; see the current PLAN.md.

PURPOSE AND SCOPE
-----------------
Reconstruct the supplied Stark Studio interface as a usable local desktop GUI.
The milestone includes real local editing, file selection, local data persistence,
theming and desktop interaction. Model inference, external search, email delivery,
CalDAV synchronization, remote authentication, agent execution and AI image
processing use explicitly labelled deterministic demo adapters. A convincing
screen alone does not complete a feature: its local flows must work.

The original 55 feature IDs are retained. Their numeric order is a reference
index, not implementation order. Dependencies below describe completion gates;
independent layout work may start earlier. A scaffold is not a completed module.
New numerical thresholds in this revision are acceptance targets, not measured
claims about the current application.

EVIDENCE AND CURRENT BASELINE
-----------------------------
Reviewed: Plan, Current Build source/README/ROADMAP, 74 screenshot references,
and sampled frames from both screencasts. The 0.01.zip, extensionless 0.02 ZIP,
and 0.03.zip are historical builds; Current Build is the implementation target.
References guide appearance/interaction, not proof that a backend must be live.
Screenshot filenames preserve the reference sequence; use full-resolution images
for feature work, not contact-sheet thumbnails as pixel-match evidence.

Observed runtime evidence is limited: PySide6 6.11.2 imported successfully; an
isolated offscreen run created the home view, opened both Theme tabs and submitted
a local message without exceptions. This does not validate interactive Wayland,
mouse dragging, desktop scaling, persistence recovery or feature completeness.

Present foundations: layered shell, sidebar animation, child tool-window manager,
16 theme definitions, 10 background effects, QSettings wrapper, basic message
cards, and three shortcuts. Most navigation routes resolve to FeaturePlaceholder.
No feature is marked Done in this revision because the full criteria below have
not yet been demonstrated.

Known gaps verified in the source/render:
- Nobody is only a checkable button, without session/persistence semantics.
- Composer is fixed at 720×96 and only adds local user labels; no session model.
- Collapsed sidebar hides Settings; account/profile is decorative.
- Theme More Colors, Density, Frosted, effect colour and Save/Import/Export lack
  working handlers; harmony generates a preview only.
- Custom palette overrides are not persisted. Fixed QSS font sizes can override
  application-level typography preferences.
- Theme Customize scroll content exposes a light background in a dark theme.
- Reopening a minimized tool does not restore it; minimized geometry can be saved
  instead of normal geometry. Drag-end persistence is not explicitly committed.
These are planning inputs, not changes made by this document.

STATUS DEFINITIONS
-------------------
Not started: no dedicated implementation found.
Scaffold: placeholder route/window only; domain behavior absent.
UI only: controls are visible but their promised behavior is unwired.
Partial: meaningful implementation exists; acceptance conditions remain unmet.
Done: every step criterion AND the common completion gate pass with evidence.
Blocked: use only with a named missing dependency and a concrete unblock action.

COMMON COMPLETION GATE — APPLIES TO EVERY STEP
---------------------------------------------
1. Every visible control works, or is disabled with a specific reason. Mock output
   is visibly labelled. No placeholder window counts as the actual feature.
2. Applicable happy, empty, invalid, loading, error, cancel and retry paths are
   exercised. Features with saved state pass close/reopen AND application restart.
3. Controls are keyboard reachable, have meaningful names and visible focus, and
   remain usable at 1100×680 logical pixels and the chosen desktop display scales.
4. Theme changes affect existing and newly opened UI; no accidental native/default
   background or unreadable selected/disabled state remains.
5. Feature state lives in a model/service, not solely in widgets. Shared command,
   registry, repository and adapter contracts are reused instead of duplicated.
6. Record the code revision/build identifier, environment, fixture, actions,
   expected/actual result and screenshot/log where useful. Never mark Done based
   only on source inspection, AST compilation or the presence of a button.
7. Use focused automated checks for state transitions, persistence, migrations,
   validation and coordinate/history logic; use manual visual checks for layout.
   Do not create tests that merely assert implementation details. Run relevant
   regression checks after changes; an unresolved acceptance failure blocks Done.

IMPLEMENTATION ORDER AND EXIT GATES
-----------------------------------
A. Stabilize shared foundations: 54, 1, 53, 39, 32, 33, 47, 35, 36, 38, 34, 37, 50.
   Exit: isolated storage, themed shared controls, reliable windows and usable
   theme/effect workflows; restart and minimum-size checks pass.
B. Settings and model configuration: 40, 41, 42, 43, 44, 46, 2, 51, 52.
   Exit: settings persist and update consumers; model/configuration flows and
   visibility controls work; secrets and mocks obey the stated boundaries.
C. Core chat/content: 10, 3, 6, 28, 7, 8, 5, 4, 9, 27, 11, 48, 49.
   Exit: normal/incognito sessions, drafts, attachments, prompt configuration,
   documents and local search work across module boundaries.
D. Personal workspaces: 13, 14, 15, 16, 31, 30, 12, 45, 17.
   Exit: persisted Brain/notes/tasks/mail/calendar flows work with demo services.
E. Research and management: 18, 19, 20, 29, 21, 22.
   Exit: comparison scores, research artifacts and Gallery metadata remain
   consistent across views, cancellation, deletion and restart.
F. Image editor: 23, 25, 24, 26.
   Exit: project round-trip, layer composition, undo/redo and complete mock AI
   preview/apply workflows pass image-based fixtures.
G. Desktop release pass: 55, plus regression of all preceding accepted features.
   Exit: documented desktop matrix, reference comparison and performance results.

Dependencies are intentionally one-way: repository contracts precede UI modules;
Library aggregates Documents and sessions; Research Library connects completed
research jobs after both sides exist; Notes consumes the scheduler. Mock data is
allowed to validate a consumer before its producer UI is complete, but the final
cross-module flow must pass before marking the consuming step Done.

ACCEPTANCE PROTOCOL AND TRACKING
--------------------------------
For each step keep a short evidence record in Current Build/acceptance/ when it
is implemented. Suggested fields: step ID, status, build/revision, date, tester,
OS/session/Qt/display scale, fixture and storage location, actions, expected and
actual result, evidence paths, remaining failures. Documentation alone is not
acceptance evidence. Mark checkboxes only after executing the corresponding check.
Update this Plan and the ROADMAP status together.

Reference comparisons:
- Match feature, selected theme, expanded/collapsed sidebar, window size and tool
  state before comparing. Record the source screenshot filename or video time.
- Check layout hierarchy, proportions, control order, spacing, typography, colors,
  borders, empty states and interaction. Native window chrome/file dialogs may
  differ intentionally; document those differences rather than claiming parity.
- Use Copper and Ocean for the detailed reference flows and Forest for home/
  background comparison; also verify Light and one other dark preset for contrast.

Shared performance fixtures (targets, to be measured on a recorded machine):
- 200 messages with mixed prose/code; 1,000 searchable content records; 500 photos
  with cached thumbnails; editor project of 2048×2048 pixels and five layers.
- After warm-up, local search at these sizes returns within 300 ms; ordinary
  selection/tab changes respond within 100 ms. Expensive I/O/decoding/processing
  shows progress promptly and does not block the GUI event loop for >100 ms.
- Background animation uses the step 36 target. Record measurement method, p95
  where applicable, and any bounded cache/history settings. Do not silently lower
  thresholds; revise the documented target with a rationale if hardware demands it.
- Repeatedly open/close ten tools and switch sessions/themes twenty times; verify
  that retained widgets, timers and background jobs do not accumulate unboundedly.

Release completion requires all 55 steps to satisfy this plan, or an explicitly
revised release scope listing deferred IDs. External backend integration is a
separate future plan with its own authentication, network, execution and service
acceptance tests. It is never inferred from a successful GUI simulation.
